# Phase 2: Token Build Pipeline - Context

**Gathered:** 2026-06-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Add DTCG token sources and Style Dictionary v5 build tooling that resolves Merce token layers into versioned Merce runtime manifest JSON files. This phase defines and proves the token build pipeline contract. It does not implement the C++ manifest registry/loader, runtime theme/variant switching, or playground gallery.

</domain>

<decisions>
## Implementation Decisions

### Token Layer Model
- **D-01:** The token pipeline must support a declared sparse theme set, not a mandatory cartesian `brand x mode` matrix. A theme may produce one manifest, or it may declare named variants such as `light` and `dark`.
- **D-02:** Themes without dark/light support must not be forced into a fake `light` default. A single-manifest theme such as `stripe` should produce `stripe.json` with no `defaultMode: "light"` assumption.
- **D-03:** Variant terminology is preferred at the output/index level. `light` and `dark` are variant names only; future variants could be `high-contrast`, `seasonal`, or another design-system-specific name.
- **D-04:** Merge order must be explicit and stable. Planning should define the exact precedence before implementation, with core values acting as fallback and theme/variant overrides layered predictably.

### Manifest Schema
- **D-05:** Style Dictionary output must be a Merce runtime manifest, not public QML token files and not raw DTCG output.
- **D-06:** Manifest fields should be close to the C++ runtime API shape, using semantic shallow names such as `palette.textPrimary`, `palette.backgroundBase`, `spacing.md`, `radius.button`, and `typography.bodyFont`.
- **D-07:** Do not duplicate old compatibility paths such as `colors.background.base` in the manifest. Existing `Theme.colors.*` compatibility should be derived inside the runtime layer when needed.
- **D-08:** The manifest must include schema/version metadata and enough theme/variant identity for Phase 3 to package and validate resources safely.
- **D-09:** The generated theme index must be authoritative for physical manifest paths. Phase 3 should read paths from the index rather than deriving paths from `theme` and `variant` names. This refines earlier roadmap/project wording that assumed physical paths like `{brand}/{mode}.json`.

### Tooling Integration
- **D-10:** Add a bounded Node/npm workspace under `tools/design-tokens` for Style Dictionary v5 tooling.
- **D-11:** npm usage is build/developer tooling only. Merce runtime and consuming Qt/QML applications must not require Node or Style Dictionary.
- **D-12:** Provide npm scripts for token build, and optionally clean/validate. CMake may expose an optional/custom token target, but the normal Qt runtime path must not become dependent on Node.
- **D-13:** Generated manifests may be committed or packaged as build artifacts so downstream consumers can use Merce without running the token toolchain.

### AI-Assisted Brand Fixtures
- **D-14:** AI may be used to read external design-system references, including `awesome-design-md` `DESIGN.md` files, and produce DTCG-compatible theme/variant token source files.
- **D-15:** AI must not produce the canonical final manifest directly. The canonical manifest is always generated by the Style Dictionary pipeline from DTCG source tokens.
- **D-16:** Real reference names such as Nike, Stripe, or Apple may be used for fixture theme names if useful; there is no project-level ban on those names for examples. Keep them as reference fixtures, not private app-specific assumptions in core Merce APIs.

### Verification
- **D-17:** Phase 2 should include schema/version validation for generated manifests.
- **D-18:** Phase 2 should include deterministic output checks, such as snapshot or diff-friendly generated output verification, so the same token inputs produce stable manifest files.
- **D-19:** Do not pull Phase 3 loader/fallback behavior into this phase. Runtime loading tests belong to Phase 3; this phase validates the build pipeline and manifest shape.

### the agent's Discretion
- Exact file names, script names, and JSON schema organization may be chosen to fit the existing CMake and repo layout.
- The planner may decide whether to add one or more external-reference fixture themes in the first plan, as long as sparse theme/variant capability is represented and the scope stays focused on token build output.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `Core/Theme/MerceTheme.h`: already exposes `Theme.palette`, `Theme.colors`, `Theme.spacing`, `Theme.radius`, `Theme.typography`, `Theme.motion`, `Theme.icons`, `Theme.zIndex`, `Theme.breakpoints`, and `Theme.shadows`.
- `Core/Theme/MercePalette.h`: gives the manifest planner a concrete target for semantic palette names such as `textPrimary`, `backgroundBase`, `actionPrimary`, and `statusError`.
- `playground/ThemeProbe.qml`: provides a small verification pattern for known public theme values, but runtime manifest loading is deferred to Phase 3.

### Established Patterns
- Merce keeps component-facing theme access behind `Theme`; components should not consume raw token files, DTCG paths, or generated manifest internals.
- Current C++ theme value getters are hardcoded. Phase 2 should generate the data contract those getters/loaders will consume later, not rewrite runtime loading yet.
- The repo already separates generated/internal token concerns from public QML module usage; preserve that boundary.

### Integration Points
- `tools/design-tokens` is the intended home for Style Dictionary configuration, custom manifest formatter, token source files, and build scripts.
- `Core/CMakeLists.txt` or top-level `CMakeLists.txt` can expose an optional token build target if useful, but normal Merce runtime use must stay independent of Node.
- Phase 3 should consume generated manifests through an index file that maps theme and optional variant names to physical paths. The loader should treat the index path as authoritative instead of deriving paths from names.

</code_context>

<specifics>
## Specific Ideas

- Candidate source layout:
  - `tools/design-tokens/tokens/core/*.json`
  - `tools/design-tokens/tokens/themes/{theme}/*.json`
  - `tools/design-tokens/tokens/themes/{theme}/variants/{variant}.json`
- Candidate generated layout:
  - `generated/themes/{theme}.json` for single-manifest themes
  - `generated/themes/{theme}.{variant}.json` for variant themes
- Candidate generated index:
  - `generated/themes/index.json`
  - `themes.stripe.path = "stripe.json"` for a single-manifest theme
  - `themes.merce.defaultVariant = "light"` plus `themes.merce.variants.light = "merce.light.json"` and `themes.merce.variants.dark = "merce.dark.json"` for variant themes
- Candidate manifest shape:
  - `schemaVersion`
  - `theme`
  - optional `variant`
  - `palette`
  - `spacing`
  - `radius`
  - `typography`
  - optional future sections for `motion`, `iconography`, `zIndex`, `breakpoints`, and `shadows`
- AI prompt direction for fixtures: read a referenced `DESIGN.md`, extract color/typography/spacing/radius signals, and emit DTCG-compatible source tokens; do not emit final Merce manifest JSON.

</specifics>
